### New Breakage in the Fix Diff

- **Minor**, `src/server/agent/session.ts` (the `#consume` catch for finding 3). The check `run.resumed && !run.initialized` treats any failure before init on a resumed run as a refused session id. That includes a missing CLI binary, a spawn error or a transient crash. In each case the panel shows "previous session could not be loaded; starting fresh" instead of the real cause, which only goes to `console.warn`. The saved id is dropped, so the next send starts a new conversation and overwrites `sessions.json`. That loses the link to a conversation that was fine. This matches the ruling's wording, so it does not block. A cheap improvement is to append the CLI's reason to the panel message. The implementer flags the same trade-off under Concerns.

### Out-of-Scope Observations

- Findings 7 and 9 change little in practice. I checked the installed SDK: `streamInput` in `node_modules/@anthropic-ai/claude-agent-sdk/sdk.mjs` waits only until the initialize request is written. After that it reads the prompt iterable eagerly and writes each message to the CLI's stdin. So after init, `InputQueue` is almost always empty, and messages queued behind a turn may still run after Stop.
  - The `readLimit: 1` fake used by both tests models a CLI that stops reading after init, which the real SDK does not do. The fake's comment says "the SDK writes nothing before the CLI is initialized". That is only true until the initialize request is written, not until the CLI's init message arrives.
  - The implementer reports this openly. Actually removing queued turns would need the CLI to drop them, or Blueprint to hold sends itself until the previous `result`. That is a decision for the controller in a later milestone.
- The Stopped row (`ClaudePanel.tsx`) shows the same running session total without the "total" label. It matches the ruling, but the two rows are now labelled differently.
- The fix range also contains two plan-only doc commits (`d6886a1`, `75abb44`) that are unrelated to these findings.
