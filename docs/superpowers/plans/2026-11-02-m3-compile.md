# Milestone 3: Compile and Tasks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Compile action produces `.blueprint/spec.md` with the fixed sections and citations, a Split action produces one task file per task through structured output, the spec and the tasks have their own views, and clicking a citation highlights the cited board elements or scrolls to the cited heading.

**Architecture:** Compile is a fixed instruction sent into the existing plan session, so the user can argue with the result in the same conversation; Claude writes `spec.md` with its own file tools. Split is a separate one-shot `query()` with `outputFormat: { type: "json_schema" }` built from a Zod `TaskGraph` schema and no tools; the server validates the answer, orders tasks by their dependencies, and writes `.blueprint/tasks/<nn>-<slug>.md` with JSON-valued YAML frontmatter that a few lines parse back. The server never rewrites Claude's spec: unknown citations are dropped when the spec is served, and the dropped list is shown as a warning. The UI gains `spec` and `tasks` routes, a read-only CodeMirror spec view whose citations are clickable marks, a tasks view with cards, and a `focus` query on board and doc routes that selects and scrolls to the cited target.

**Tech Stack:** The milestone 2 stack; Zod 4's `z.toJSONSchema` for the output schema; CodeMirror decorations for citation marks. No new dependencies.

**Spec:** `docs/build-plan.md` (sections 4, 5 `spec.md` and `tasks/`, 6.3 citations, 6.6, 7, 8 row 3, 9, 10). Milestones 1 and 2 are on `main`; this plan builds on `Agent`, `agentRoutes`, `routes`, `FileStore`, `ClaudePanel`, `useHashRoute`, `DocView`, `BoardView`, and the export module's `parseCitations`, `buildCitationIndex`, `dropUnknownCitations`, and `headingSlugs`.

Calls made for this plan where the spec is silent:

- Task frontmatter values are JSON literals (`title: "Auth"`, `dependsOn: ["db"]`), which is valid YAML and needs no YAML dependency to write or read.
- Task files are numbered in a dependency-respecting order (a stable topological sort of the returned graph), and a Split replaces the whole `tasks/` directory; git keeps history, as it does for the spec.
- The split query runs with no tools and the spec text inline, so it spends one turn; its cost is shown in the tasks view.
- The spec view is CodeMirror in read-only mode, consistent with the doc view; Markdown rendering is the milestone 5 design pass's call.
- A citation click navigates by hash (`#/boards/<name>?focus=<id>,<id>` or `#/docs/<file>?focus=<slug>`), so a highlighted target is a shareable URL and the back button works.

## Global Constraints

- Node 22.1 or later; TypeScript strict; ESM; server code uses NodeNext resolution with explicit `.js` extensions on relative imports.
- No API key anywhere. Both the plan session and the split query run on the user's Claude Code login.
- `spec.md` has exactly these level-2 sections in this order: `Goals`, `Architecture`, `Interfaces`, `Constraints`, `Acceptance criteria`, `Open questions`.
- Citations use `[[board:<name>#<elementId>]]` and `[[doc:<file>#<heading-slug>]]`; unknown citations are dropped with a warning when the spec is served and never rewritten on disk.
- Task files live at `.blueprint/tasks/<nn>-<slug>.md`; `nn` is two digits from `01`; slugs match `src/shared/slug.ts`'s rule.
- All agent output reaches the browser as typed WebSocket messages; commands go through HTTP routes so they are testable with `app.request()`.
- No "Claude Code" branding in UI copy.
- Every UI test file that renders components or hooks starts with `// @vitest-environment jsdom`.
- Commit messages use conventional commits and carry no co-author trailer.
- `pnpm check` stays pristine; `pnpm build` warns only about the pre-existing chunk size.

## Review Focus

1. Split returns a task graph with a cycle, a duplicate slug, or a dependency on an unknown slug: the server must reject it with a message naming the problem and write nothing, not half a directory. Pinned in Task 1 (`orderTasks`) and Task 4.
2. The structured output never validates (the SDK gives up after its retries) or the query fails to start: the tasks view must show the error, the previous task files must survive, and the UI must not stay in `Splitting`. Pinned in Task 4 and Task 7.
3. A citation to an element that was deleted after compiling: the spec view shows it as dropped, and clicking the remaining ones still works. Pinned in Task 2 and Task 6.
4. Compile while the plan session is mid-turn: the instruction queues like any message and the panel shows it; a second Compile click while one is queued must not send twice. Pinned in Task 3 and Task 5.
5. A board route with a `focus` that names an element on another board or that no longer exists: the board opens, nothing is selected, and no error is thrown. Pinned in Task 6.

```ts
import { z } from "zod";
export const Task = z.object({
  slug: z.string().regex(SLUG_RE), title: z.string().min(1), body: z.string(),
  dependsOn: z.array(z.string()), files: z.array(z.string()), acceptance: z.array(z.string()),
  sources: z.array(z.string()),
});
export type Task = z.infer<typeof Task>;
export const TaskGraph = z.object({ tasks: z.array(Task).min(1) });
export type TaskGraph = z.infer<typeof TaskGraph>;
export type TaskFile = { file: string; task: Task };           // file is "<nn>-<slug>.md"
export function orderTasks(tasks: Task[]): Task[];             // stable topological order; throws Error("duplicate task slug <s>"), Error("task <s> depends on unknown task <t>"), or Error("tasks <a> and <b> depend on each other") naming the first problem found

export function taskToMarkdown(task: Task): string;            // frontmatter with JSON values for title, dependsOn, files, acceptance, sources; then a blank line and the body
export function taskFromMarkdown(text: string): Task;          // throws Error("task frontmatter: <reason>") on a missing fence or a line that is not `key: <json>`
```

**Interfaces:**

- Produces in `src/server/agent/split.ts`:

```ts
export const SPLIT_PROMPT: (spec: string) => string;
   // asks for 3 to 12 implementation tasks, each independently testable, with kebab-case slugs, dependsOn by slug, files likely touched,
   // acceptance checks, and sources copied verbatim from the spec's citations; the spec text follows under a "## Specification" heading
export async function splitSpec(deps: { query: typeof import("@anthropic-ai/claude-agent-sdk").query; cwd: string }, spec: string): Promise<{ tasks: Task[]; costUsd: number | null }>;
   // one query() with prompt SPLIT_PROMPT(spec) and options { cwd, maxTurns: 2, tools: [] (if `tools` is not an `Options` field in the installed SDK, use `disallowedTools` naming every file, shell, and web tool instead and say so in the report), permissionMode: "default", outputFormat: { type: "json_schema", schema: z.toJSONSchema(TaskGraph) } };
   // reads the result message: subtype "success" with structured_output parsed by TaskGraph → tasks; any other subtype or an invalid output → throws Error("split failed: <errors or zod message>")
```

- Produces on `Agent`: `split(): Promise<void>` reads the spec (throws `NotFoundError("compile the plan first")` when null), broadcasts `split.status running`, runs `splitSpec`, calls `store.replaceTasks`, broadcasts `done` with `costUsd` (or `error` with the message), and refuses a second split while one runs (`Error("a split is already running")`).
- Produces in `src/server/agentRoutes.ts`: `POST /split` → 202 when started, 404 when there is no spec, 409 while one runs.
